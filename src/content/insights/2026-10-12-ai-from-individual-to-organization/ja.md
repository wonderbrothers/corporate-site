対象期間：2026年10月5日〜11日

AIを使って、資料や画面、コードを短時間でつくれるようになりました。しかし、個々の作業が速くなることと、サービスの改善や事業の成果が早く届くことは同じではありません。レビューや承認で待ち時間が生まれたり、確認作業が増えたりすれば、制作段階の効率化だけでは十分な効果を得られないからです。

今週は、業務フローの再設計、AI開発の品質管理、デザインシステムの保守、職種を横断する学習など、導入したAIを組織の仕事に組み込むための動きが見られました。端末内とクラウドを使い分けるAIの発表も、情報の扱い方や利用者の同意を設計する課題につながります。

これらの動向を、確認できる事実、その意味を読み解く示唆、現場で試せる行動の3つの視点で紹介します。

## 1. 個人の生産性向上を、業務全体の成果につなげる

### FACTS

McKinseyは10月5日公開の記事で、同社の2026年AI調査を引用しました。回答者の80％がAIによる個人の生産性向上を報告した一方、EBIT（利払い・税引き前利益）へのプラス効果を報告した割合は37％でした。

また、同社が高成果企業に分類した組織の約4分の3は、業務フローを大幅に再設計したと回答しています。その他の組織では約4分の1でした。

これは回答者の申告に基づく結果です。業務フローの再設計と高い成果の関連は示していますが、再設計だけが成果を生んだと証明するものではありません。また、10月5日は記事の公開日であり、調査の実施日ではありません。

出典：McKinsey  
[AI is changing work. Now it has to change the organization](https://www.mckinsey.com/capabilities/people-and-organization/our-insights/ai-is-changing-work-now-it-has-to-change-the-organization)（2026年10月5日）

### INSIGHT

この結果から考えたいのは、AI導入の評価単位です。担当者が何時間節約できたかに加えて、その後の工程まで含めて仕事がどう変わったかを見る必要があります。

たとえば、画面設計の時間が半分になっても、仕様の確認に数日かかり、実装後に認識のずれが見つかる状態なら、公開までの期間は大きく変わらないかもしれません。これは仮の例ですが、制作速度と業務全体の速度を分けて考える理由になります。

デザインやDXの対象には、画面だけでなく、誰が何を確認し、どの情報で判断し、次の担当者へ何を渡すかという仕事の設計も含まれます。

### ACTION

一つの機能改善を対象に、企画から公開までの工程を並べ、各工程の「作業時間」「待ち時間」「手戻り」を記録します。

そのうえで、最も長い待ち時間を生む箇所を一つ選び、確認資料や承認手順を小さく変更します。変更前後で、公開までの日数が短くなったか、手戻りや利用者の問題が増えていないかを確認してください。

## 2. AI開発では、生成したコードを公開するまでの仕組みが問われる

### FACTS

GitLabは10月6日、企画から本番公開までを組織の方針と基準に沿ってつなぐ「Governed Software Factory」の基盤を発表しました。

発表には、工程間の作業をつなぐエージェント機能、成果物管理、問題のある依存パッケージの制御、AIの費用と成果を把握する分析機能などが含まれます。

提供段階は一律ではありません。成果物管理のGitLab Artifact CentralはGitLab.comでベータ提供され、Self-Managed版は同月後半を予定。Duo Agent Platform Impact Analyticsは早期アクセスです。セキュリティ対策の評価基準であるGitLab Security Standardは、発表時点で利用可能とされています。

出典：GitLab  
[GitLab Announces the Foundation for the Governed Software Factory](https://about.gitlab.com/press/releases/2026-10-06-gitlab-announces-the-foundation-for-the-governed-software-factory/)（2026年10月6日）

### INSIGHT

AIによって実装量が増えると、レビューやテスト、承認に必要な仕事も増えます。コードを書く工程だけを自動化すると、確認の負荷が後工程へ移る可能性があります。

今回の発表は、生成から公開までを一続きの工程として扱う方向を示しています。ただし、ツールを導入するだけで、製品ごとの品質基準まで決まるわけではありません。

UXの観点では、処理が成功することに加え、失敗したときに戻れるか、操作できない人を生んでいないか、利用者が次に何をすべきかわかるかを、公開判断に含める必要があります。

### ACTION

AIで実装する機能を一つ選び、着手前に受入条件を明文化します。たとえばフォームなら、入力エラー、通信失敗、二重送信、キーボード操作、フォーカス移動を確認対象にします。

変更内容にテスト結果と承認者をひも付け、レビュー時間、差し戻し回数、公開後の不具合を記録します。生成速度が上がっても確認負荷が増える場合は、自動化する範囲を見直します。

## 3. 端末内とクラウドを使い分けるAIは、情報と権限の設計を変える

### FACTS

Microsoftは10月7日、端末内とクラウドのAIを組み合わせるWindowsの「Hybrid Intelligence」を発表しました。用途に応じた処理の振り分けに加え、端末内の情報参照や操作を扱う構想を示しています。

GitHub Copilotアプリ、CLI、Visual Studio Codeに向けた関連機能は、10月後半に実験的プレビューを予定。Copilot+ PC向けの関連機能は、今後数か月で展開を始める予定です。端末、市場、ハードウェアによって利用条件や時期が異なり、10月7日時点で全面提供されたものではありません。

出典：Microsoft  
[Building Windows for hybrid intelligence](https://blogs.windows.com/windowsexperience/2026/10/07/building-windows-for-hybrid-intelligence/)（2026年10月7日）

### INSIGHT

企業向けAIの選定では、回答の性能に加え、どの情報をどこで処理するかが判断材料になります。端末内で扱うことが適切な情報と、クラウドを利用してよい情報を、業務ごとに整理する必要があります。

UXにも影響があります。利用者がファイルの参照を許可したことと、その内容を外部へ送ることや、ファイルを書き換えることに同意したことは同じではありません。

「AIの利用を許可する」という一つの設定にまとめず、参照、送信、実行を区別して理解できる体験を考えることが重要です。

### ACTION

ファイルを扱うAI機能を一つ選び、参照する情報、外部へ送る情報、実行する操作を一覧化します。

その内容を確認できる画面を試作し、想定利用者に「何を許可したか」「どこへ情報が送られるか」「実行を止めるにはどうするか」を説明してもらいます。説明できなかった箇所を修正し、権限を与えない場合でも仕事を続けられるかを確かめます。

## 4. デザインシステムの維持に、AIを組み込む方法が具体化する

### FACTS

Figmaは10月6日、エージェントを使ったデザインシステムの保守方法を公開しました。仕様書の下書き、命名の統一、デザイントークンの使用状況の点検、既存コンポーネントへの置換などを紹介しています。

Uberではコンポーネントの仕様説明や色の仕様作成、Granolaでは取り込んだ画面の部品を既存のデザインシステムへ対応させる事例が紹介されています。いずれもFigmaによる事例紹介であり、一般的な削減効果を示す独立した比較試験ではありません。

記事時点では、対象プランのFull seatを中心に利用可能とされ、Starterプランは限定提供、Collab・Dev・View seatでは下書き内で利用できるなど、条件があります。

出典：Figma  
[How to lighten design system upkeep with the Figma agent](https://www.figma.com/blog/figma-agent-and-design-systems/)（2026年10月6日）

### INSIGHT

デザインシステムは、部品をそろえて完成するものではありません。製品の変更に合わせて仕様を更新し、例外を判断し、画面と実装のずれを修正し続ける必要があります。

AIを保守に使う意味は、人が見落としやすい不整合を探し、判断が必要な箇所を絞ることにあります。一方、見た目が似た部品でも、用途や操作上の意味が異なる場合があります。すべてを機械的に統一すればよいわけではありません。

どこまでを共通化し、どの例外を残すか。その理由を説明できることが、保守の自動化にも役立つと考えられます。

### ACTION

代表的な3画面を複製し、既存コンポーネントとの対応、色や余白の直書き、命名の不一致を点検します。最初は自動修正せず、検出結果を人が確認する運用にします。

検出数、誤検出、見逃し、確認と修正にかかった時間を記録してください。置換後は、状態表示やコントラストなども確認し、見た目の統一と使いやすさが両立しているかを判断します。

## 5. AIの学習は、操作方法から成果を判断する力へ

### FACTS

Figmaは10月10日、Figma、Sephora、Mercari、AtlassianのAI学習に関する取り組みを紹介しました。

Figmaでは、関心のある技能ごとに少人数の学習グループを設け、週1時間、6週間の実践を実施。Sephoraでは、完成品中心の発表から、試した過程や失敗も共有する形式へ変更しています。Mercariでは、デザイナーが開発の基礎を、開発者が視覚的な優先順位などデザインの基礎を学ぶ取り組みが紹介されています。

記事は各社の実践報告であり、研修方法の優劣を比較検証した研究ではありません。また、10月10日は紹介記事の公開日です。

出典：Figma  
[4 team rituals that drive AI adoption](https://www.figma.com/blog/4-team-rituals-that-drive-ai-adoption/)（2026年10月10日）

### INSIGHT

AIによって専門外の成果物をつくりやすくなっても、その品質を判断する知識まで同時に身につくとは限りません。

たとえば、デザイナーが動く画面をつくれたとしても、保守性や権限管理の確認には開発の知識が必要です。開発者がUIを生成した場合も、情報の優先順位や利用者の理解を検証する視点が必要になります。これらは役割の広がりを考えるための例です。

チームの学習では、使い方の共有に加え、「何を良いと判断するか」「どこから専門家の確認が必要か」を共有することが重要になります。

### ACTION

定例の15分を使い、AIでつくった成果物を別職種がレビューする機会を設けます。完成品だけでなく、最初の出力、問題点、修正の過程を一つずつ共有します。

次の担当者が同じ方法を再現できたか、同じ問題を早く発見できたかを確認します。参加人数や発表回数だけでなく、再利用できた判断基準を学習の成果として残します。

## 今週の優先アクション

1. **一つの業務の作業時間と待ち時間を記録する。**  
   最初に着手したいのは現状の把握です。改善前の状態がわからなければ、AIが成果を生んだのか、負荷を別の担当者へ移したのかを判断できません。
2. **AIでつくる機能の受入条件を、着手前に決める。**  
   正常に動くことに加え、失敗時の復帰、権限、アクセシビリティ、確認責任を整理します。公開直前の手戻りを減らすための準備です。
3. **既存3画面のデザインシステム監査を試す。**  
   対象を限定し、検出精度と人の確認時間を測ります。新規制作の速さだけでなく、維持管理の負担を減らせるかを確かめます。
