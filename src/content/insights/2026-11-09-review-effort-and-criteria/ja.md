対象期間：2026年11月2日〜8日

AIによる制作や業務実行の選択肢が増えるほど、成果物を確かめる仕事も変わります。指示を書き足す負担はどれくらいか。人によって異なる「よい」の基準をどう共有するか。試作の操作や、継続稼働するエージェントの権限をどこまで確かめるか。今週の動向には、こうした判断を具体化する材料がありました。

生成の速さだけで導入効果を測ると、確認や手直しに移った負担を見落としかねません。作る工程と確かめる工程を一緒に捉えることが、プロダクト開発にも業務設計にも役立ちます。

## 1. UXの改善作業は、AIを加えるほど軽くなるとは限らない

11月2日のBritCHI公式プログラムに掲載された論文は、UX実務者30人を10人ずつの3群に分け、車載システムの評価指針を作る作業を比較しました。初期案は全群がAIで作成し、その後を「AIのフィードバックとAIによる修正」「専門家のフィードバックと手作業の修正」「専門家のフィードバックとAIによる修正」に分けています。全体の作業負荷、信頼、技術受容には群間の有意差がありませんでしたが、専門家の指摘をAIで反映する群では、手作業で反映する群より精神的負荷が高いという下位尺度の差が出ました。

とはいえ、この結果からAIが修正に向かないとまでは言えません。単一の車載コンセプトとローカルのLlama 3 8Bを使った小規模な実験で、最終成果物の品質も独立評価されていません。それでも、専門家の指摘をAIへの指示に翻訳し、返ってきた修正を再確認する工程が、利用者の負担になり得る点は実務上の論点です。主観的な負荷と実際の所要時間も分けて考える必要があります。

まずは既存のUXレビュー項目を一組選び、同じ指摘を人が反映する場合とAIが反映する場合を比べるのが現実的です。生成待ち時間だけでなく、指示作成、確認、再修正の時間を記録し、別の担当者が抜けや誤修正を評価するとよいでしょう。作業全体で比べることで、AIに任せやすい修正と、人が直接直した方がよい修正の境界が見えてきます。

出典：[Appropriate Automation in AI-Assisted Usability Heuristic Generation: Comparing Human-AI Collaborative Workflows](https://www.britchi.uk/proceedings/7018.pdf)（BritCHI 2026論文集、2026年11月2日の[公式セッションプログラム](https://www.britchi.uk/programme/schedule/paper-session-1-ai-expertise-and-changing-practice/)に掲載）

## 2. 曖昧な評価基準を、境界にある具体例から詰める

Google Researchは11月4日、「Agile Deliberation」を紹介しました。これはCVPR 2026で発表済みの研究を解説したもので、今週初めて公表された研究結果ではありません。「健康的な食べ物」など判断の揺れやすい概念について、含むものと除くものを定義し、AIが提示する境界的な画像を人が検討して、分類基準とプロンプトを改善する方法です。研究では2領域を対象に、各1.5時間のセッションを18回実施し、著者らは比較手法に対する判断の一貫性や性能の改善を報告しています。

ここで参考になるのは、曖昧な指示を長文化するだけでなく、判断が割れる例を使って基準そのものを調整する進め方です。デザインでも「ブランドらしい」「誤解を招かない」といった言葉は、合意したつもりでも担当者によって意味が異なります。この研究は画像分類の限られた課題であり、そのままデザイン審査の効果を保証するものではありませんが、意見の違いを観察する方法として応用の余地があります。

たとえば広告表現の「誤解を招かない」という基準について、判断が割れそうな10例を用意し、複数人が独立に判定するところから始められます。不一致の理由を基準へ反映し、議論に使わなかった例でも一致するかを確かめるとよいでしょう。そこで残る不一致は、AIへの指示不足なのか、人の間でも未合意の判断なのかを切り分ける材料になります。

出典：[Agile Deliberation: How AI helps humans define the gray areas](https://research.google/blog/agile-deliberation-how-ai-helps-humans-define-the-gray-areas/)（Google Research、2026年11月4日）

## 3. Figmaのプロトタイプ接続が、コード生成の文脈になる

Figmaは11月3日、デザインフレームからcode layerを作成する際に、エージェントがプロトタイプの接続やインタラクションを読み取る更新を発表しました。code layersは引き続きオープンベータです。画面の見た目に加えて、画面同士のつながりをコード生成へ渡せるようになる変更であり、本番品質や実装時間の改善を数値で保証した発表ではありません。

これにより、プロトタイプで定義した振る舞いが、実際に操作できる試作へ引き継がれる可能性が広がります。同時に、元の設計にない分岐が正しく補われるとは限りません。通常の完了経路だけを接続した試作では、取り消し、入力エラー、前の画面へ戻る操作といった、現場で頻繁に起こる動きが検証から抜け落ちやすくなります。

小さく試すなら、既存の申し込みフローを一つ選び、通常経路と例外経路の接続を明示した上でcode layerを作成する方法があります。期待した遷移の再現率と修正時間に加え、キーボードだけで完了できるか、エラー後にフォーカスを見失わないかも比較対象になるでしょう。見た目の近さと操作の再現性を別々に測ることで、実装へ進める前にどの設計情報を補うべきかが明確になります。

出典：[Your prototype connections, now context for code layers](https://www.figma.com/release-notes/)（Figma Release Notes、2026年11月3日）

## 4. 常時稼働エージェントは、一般提供と利用開始の条件を分けて読む

OpenAIは11月4日、会話の間もタスクを継続するDotsを、対象となるChatGPT Enterprise、Edu、Healthcareのワークスペースで一般提供すると発表しました。管理者向けプレビューは11月18日までで、その間に所有者・管理者が利用を有効化するか、既定で利用可能になる前にオプトアウトする構成です。UAEのデータまたは推論レジデンシーを設定したワークスペースは対象外とされています。

管理者は利用できるメンバーを制御し、Dotsと接続先を確認して、一時停止・再開や利用状況・管理操作の確認を行えます。所有者には削除権限もあります。新規DotsはデータレジデンシーとEnterprise Key Managementに対応し、推論レジデンシーはEU・米国をサポートします。対象環境で一般提供前に作成されたDotsは、提供開始から30日以内に必要な地域へ移行するという条件も付いています。一般提供という区分だけでなく、利用開始日、既存データの移行、管理者の権限を併せて読む必要があります。

導入を判断する際は、11月18日までに少人数の対象業務と接続先を絞り、稼働中の一時停止、接続権限の取り消し、再開を試すとよいでしょう。「今後の処理が止まること」と「既に行われた変更が元に戻ること」は別の要件として、確認できた範囲を記録するのが有効です。停止操作の結果と作業履歴を突き合わせれば、利用者への説明や障害時の対応手順に何が不足しているかを把握できます。

出典：[Dots for Enterprise, Edu, and Healthcare](https://openai.com/products/release-notes/)（OpenAI Release Notes、2026年11月4日）

## 今週の優先アクション

1. **利用開始の期限がある機能から、対象と権限を整理しておく。** Dotsの対象ワークスペースでは、11月18日までに利用対象、接続先、停止責任者を決めるところから始めるのが現実的です。既定で利用可能になる前に、小さな範囲で運用条件を確かめられます。
2. **一つの制作工程で、生成から確認・修正までの負担を測ってみる。** UXレビューの修正などを対象に、人が直接行う場合との総時間と品質を比較すると、導入効果を生成速度だけで判断することを避けられます。
3. **判断が割れる例を、チームの評価資産として残しておく。** 曖昧な品質基準やプロトタイプの例外経路を具体例にし、未使用の例でも判断や動作が再現されるかを確かめることで、次の試作にも使える基準が蓄積します。
